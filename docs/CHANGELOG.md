Not a feature milestone: prepares the already feature-complete Version 1.0 implementation for real-world deployment. No application features were added; everything here is infrastructure, deployment configuration, and operational documentation.

- **Test coverage for previously-untested security primitives**: `InMemoryRateLimiter` (zero prior coverage despite backing a P0 requirement) and the confidential-document MIME allow-list.

### Fixed — Security

- **Login rate limiting now actually enforces "per account AND per IP" independently** (FR-AUTH-05/NFR-SEC-07). Previously used one composite key (`login:${email}:${ip}`), which only throttled the exact pair — an attacker varying either dimension (many emails from one IP, or one email from many IPs) never accumulated against a shared limit, silently defeating the documented requirement. Now performs two independent `consume()` calls (`login:email:...`, `login:ip:...`), rejecting if either is exhausted.
- **JWT signing/verification now explicitly pins `algorithm: "HS256"`/`algorithms: ["HS256"]`**, rather than relying on `jsonwebtoken`'s implicit default behavior for a string secret. Not currently exploitable (the library already restricts a string-keyed `verify()` to HMAC algorithms), but closes the "algorithm confusion" vulnerability class defensively against future library-default changes.
- **Confidential document metadata registration now validates `mimeType` against an allow-list** (`application/pdf`, `image/jpeg`, `image/png`) rather than accepting an arbitrary string, per NFR-SEC-06. Full content-signature validation remains blocked on the not-yet-built file-upload endpoint itself (this module only ever registers a reference to a file uploaded elsewhere) — tracked in `TECHNICAL_DEBT.md`.

### Fixed — Architecture

- **Removed a duplicate `http-errors.ts`** in the auth module (predated the shared `src/lib/http-errors.ts` from Days 3–4, kept alive only because it had one function — `tooManyRequests` — the shared version lacked). Added `tooManyRequests` to the shared file, repointed all three consumers, deleted the duplicate.
- **Added a missing `try/catch` in the batch-creation route handler** for `NotAuthorizedError`, matching every sibling route handler's defense-in-depth pattern. Currently unreachable via the route's own role gate, but would have surfaced as a raw 500 instead of a clean 403 if the use case were ever reused from a less-restrictive route.

### Fixed — Accessibility

- `FieldError` (shared by every form) gained `role="alert"` so validation errors are announced to assistive technology when they appear.
- `TableHeaderCell` gained `scope="col"`.
- The admin/recruiter shell's active nav link gained `aria-current="page"` (previously conveyed by color alone).
- The profile-review "request changes" textarea gained a proper `<Label>` (previously relied on a `placeholder` alone, which is not a reliable accessible-name substitute).

### Verified, no change needed

Documented in full in the five reports above; highlights: refresh-token rotation/reuse detection, cookie configuration (httpOnly/Secure/SameSite=Strict, path-scoped), the full RBAC permission matrix and `withAuth`'s four-step flow, every DTO whitelist regression test (exports/recruiters/notifications), the one raw SQL query in the codebase (parameterized, not injectable), color contrast against the actual design tokens, and zero N+1 query patterns anywhere in the codebase.

## 2026-08-05 — Background Job Processing System

Architectural requirement, not a numbered roadmap day: generalize the Job table (frozen since Day 1, unused until now) into a full, reusable background-processing foundation, and refactor the Notification Architecture milestone's synchronous email send onto it — its `NotificationService.notify()` was already designed to hide *how* delivery happens, so this refactor is the first real test of that abstraction.

### Added

- **New `jobs` module** (`src/modules/jobs`), a generic, domain-agnostic job queue: dispatcher, registry, handler abstraction, worker, retry/backoff policy — all framework-free except the one Prisma-backed repository. No other module's business logic lives here; `type` is a free-form string this module never enumerates, so it never needs to change when a new background job is added elsewhere.
- **`JobDispatcher`** (`application/job-dispatcher.ts` + `DefaultJobDispatcher`): the only thing a producer module depends on to enqueue work — `dispatch(type, payload, { runAt?, maxAttempts? })`. Knows nothing about workers, retries, or handlers.
- **`JobRegistry`** (`application/job-registry.ts`): a handler registration map (`register`/`get`/`has`/`registeredTypes`). Registering two handlers for the same type throws — adding a job type is additive, never a silent override.
- **`JobHandler`** (`application/job-handler.ts`): the interface every background job type implements — `handle(payload)` plus an optional `onPermanentFailure(payload, error)` hook, called once after the worker exhausts retries, for a handler that needs to react to permanent failure (see notifications' integration below) without re-implementing retry logic itself.
- **`JobWorker`** (`application/worker/job-worker.ts`): polls, atomically claims a batch, and executes each job sequentially against whatever handler `JobRegistry` has for its type — no switch statement, no per-type branching. Unknown types (a job whose type has no registered handler) are dead-lettered immediately rather than retried. `start()`/`stop()` support graceful shutdown: `stop()` stops claiming new batches but awaits whatever job is currently executing before resolving, so a job is never abandoned mid-execution.
- **Retry policy** (`domain/retry-policy.ts`): `shouldRetry(attempts, maxAttempts)` and `computeBackoffMs(attempts)` — exponential backoff (1s, 2s, 4s, ... capped at 5 minutes) with ±20% jitter (so a burst of jobs that failed at the same instant, e.g. an email provider outage, don't all retry in lockstep and re-overwhelm it the moment it recovers). Pure functions, fully unit-tested independent of the worker.
- **Structured logging and metrics hooks**: `JobLogger` (`info`/`warn`/`error`, one JSON line per event) and `JobMetricsRecorder` (`recordJobStarted`/`Completed`/`Failed`/`Retried`) are both ports with a console-based Version 1.0 default (`ConsoleJobLogger`, `ConsoleJobMetricsRecorder`). Swapping either for a real backend (pino/Datadog/Prometheus/CloudWatch) later is a new implementation of the port; `JobWorker` is unaffected.
- **`Job` table extended, not replaced**: `attempts`, `runAt`, `type`, `payload`, `status` already existed (Day 1); added `maxAttempts`, `lastAttemptAt`, `nextRetryAt`, `completedAt`, `errorMessage`, `executionTimeMs`, and `lockedBy` (which worker currently/last held this job, for observability — not itself the concurrency-safety mechanism; see Security Decisions). `JobStatus` gained `RETRYING`/`CANCELLED` and renamed `RUNNING`→`PROCESSING`/`COMPLETE`→`COMPLETED` (see Deviations).
- **Atomic claiming** (`infrastructure/prisma-job-repository.ts`): `claimBatch()` uses a raw, parameterized `UPDATE ... WHERE id IN (SELECT ... FOR UPDATE SKIP LOCKED) RETURNING *` — the standard Postgres job-queue pattern — so concurrent worker processes can never claim the same job, and one worker never blocks waiting on rows another is mid-claim on. Not expressible through Prisma's fluent query builder, hence the one piece of raw SQL in this module.
- **Worker entrypoint** (`scripts/run-worker.ts`, deliberately outside `src/`, outside the Next.js request pipeline): `npm run worker` runs a long-lived polling daemon with graceful SIGTERM/SIGINT shutdown; `npm run worker:once` claims and processes a single batch then exits, for a platform with no persistent-process support (an external scheduler/cron/Scheduled Function invoking it periodically instead) — the hosting platform is still an open decision (`docs/planning/18_Open_Questions.md`, Q1), and this script works either way without that decision being made first. Registering a new module's handlers is the one place adding a background job touches outside that module itself; `JobWorker`'s own code never changes.
- **Notification Architecture refactor**: `DefaultNotificationService.notify()` no longer sends anything itself — it creates the `Notification` audit-trail row (`PENDING`) and enqueues a `SEND_NOTIFICATION` job via `JobDispatcher`, carrying the `notificationId` plus the original request. The actual recipient lookup, template rendering, and `EmailProvider.send()` moved into a new `NotificationJobHandler` (`notifications/infrastructure/notification-job-handler.ts`), run later by a `JobWorker` — possibly in a separate process. **`ApproveDraftUseCase` and `RequestChangesUseCase` (profiles module) required zero changes** — `NotificationService.notify()`'s signature and "never rejects" guarantee are identical before and after this refactor, exactly what that abstraction was built for.
- **Tests** (507 passing, up from 467): job creation/claiming/state-transition unit tests against a fake repository that reproduces the same atomic-claim contract `FOR UPDATE SKIP LOCKED` guarantees in production (duplicate-claim prevention verified directly: two sequential claims never return overlapping jobs); `JobRegistry` registration/duplicate-type tests; `computeBackoffMs`/`shouldRetry` unit tests (deterministic via an injectable `random` function); a comprehensive `JobWorker` suite (successful execution, retry-then-recover, dead-letter after exhausting `maxAttempts` with `onPermanentFailure` invoked exactly once, a failing permanent-failure hook itself logged but never thrown, unknown-type dead-lettering, two independent workers sharing one repository never double-executing a job, `start()`/`stop()` lifecycle including a deterministic graceful-shutdown ordering test); a rewritten `DefaultNotificationService` suite for the new job-enqueuing behavior; a new `NotificationJobHandler` suite (send success, no-email-on-file handled as permanent without throwing, provider failure *propagates* rather than being swallowed, `onPermanentFailure` marks the `Notification` row); and a full end-to-end integration test (`notify()` → job enqueued → `JobWorker.pollOnce()` → email "sent" → `Notification` row `SENT`), including its retry and dead-letter paths.

### Architectural decisions

- **Job execution within a claimed batch is sequential, not concurrent.** Keeps graceful shutdown trivial to reason about (`stop()` only ever has to wait for one in-flight job) and avoids one worker process hammering a single downstream dependency (an email provider, an export renderer) with a burst of concurrent calls. Horizontal scaling is running multiple `JobWorker` processes, not concurrency within one — nothing in this design assumes a single worker exists; `claimBatch`'s atomicity is what actually prevents double-execution, not an in-process mutex.
- **`JobHandler.handle()` always takes `Record<string, unknown>`, never a handler-specific generic type.** `JobRegistry`/`JobWorker` store and invoke handlers uniformly and can't know each type's real payload shape; a narrowed generic parameter on the interface breaks structural assignability the moment a handler is registered into the shared registry. Each handler casts/validates its own payload at the top of `handle()` instead (see `NotificationJobHandler`) — the same tradeoff every message-queue library with a heterogeneous handler registry makes.
- **`NotificationJobHandler` does not catch `EmailProvider` failures itself — it lets them propagate.** The whole point of building a generic retry/backoff/dead-letter policy once is that individual handlers don't reimplement it. Only `onPermanentFailure` (called once, after `JobWorker` gives up) touches the domain-specific `Notification` row's terminal state — keeping "is this transient, should we retry" entirely with the worker's generic policy, and "what does permanent failure mean for *this* job type" entirely with the handler.
- **The `Notification` table (audit trail: who was notified, via what channel/template, delivered or not) and the `Job` table (generic execution bookkeeping: attempts, backoff, worker claims) are kept as two separate concerns, not collapsed into one.** A `notificationId` travels inside the job payload as the correlation key. This means a future "sent notifications" view can query `Notification` directly without needing to know anything about job-processing internals, and the generic `Job`/`JobWorker` machinery never needs to know what a "notification" is.
- **A recipient with no email on file is treated as a permanent, first-attempt condition inside the handler (`Notification` marked `FAILED`, `handle()` returns normally), not an exception that triggers the worker's retry policy.** Retrying can never make a missing email address appear; treating it as a job failure would just burn through `maxAttempts` for a condition retrying can't fix.
- **`jobRegistry`/`jobDispatcher` are exported as live, eagerly-constructed singletons from `jobs/infrastructure/container.ts`** (the same pattern as auth's `withAuth` and notifications' `notificationService`) since neither depends on secrets. **`createJobWorker()` is a factory, not a singleton** — constructing a worker never starts it; starting one is an explicit act performed only by `scripts/run-worker.ts`, never an accidental side effect of importing `@/modules/jobs` from a web request.
- **Handler registration is an explicit function call (`registerJobHandlers()`), never a side effect of importing a module.** `notifications/infrastructure/container.ts` exports both `notificationService` (safe to import from anywhere, no secrets touched) and `registerJobHandlers()` (constructs the env-derived `EmailProvider`, so only called explicitly by `scripts/run-worker.ts`) — the same "importing a module for one export must not force unrelated secret validation" lesson from Days 2–3's auth container bug, applied here proactively rather than discovered by a broken test.

### Security decisions

- **The atomic claim query is parameterized (Prisma's tagged-template `$queryRaw`), never string-concatenated**, despite being the one place in this module that can't use Prisma's fluent builder — avoiding SQL injection in the one raw-SQL code path this module has.
- **Duplicate-execution prevention is a database-level guarantee (`FOR UPDATE SKIP LOCKED` inside the same statement that flips a row to `PROCESSING`), not an application-level lock.** An application-level mutex/semaphore would only work within one process; this holds across any number of concurrent worker processes, which is the actual requirement ("can be scaled to multiple workers in the future").
- **A permanent-failure hook throwing is caught and logged by `JobWorker`, never left to crash the poll loop or the whole worker process.** A bug in one job type's failure-handling code must not take down processing for every other job type sharing the same worker.

### Deviations from documentation, flagged rather than assumed

- **`JobStatus` values changed**: `RUNNING`→`PROCESSING`, `COMPLETE`→`COMPLETED`, plus new `RETRYING`/`CANCELLED` values — `docs/database/08_Database_Design.md` still documents the original `PENDING, RUNNING, COMPLETE, FAILED`. Safe because the `Job` table had zero production usage before this change (confirmed: no code anywhere referenced `prisma.job` or `JobStatus` prior to this milestone) — nothing depended on the old values. Same pattern, same justification, as the Days 5–6 `ProfileDraftStatus` `REJECTED`→`CHANGES_REQUESTED` rename.
- **Notification delivery is now asynchronous (queued), reversing the Notification Architecture milestone's own documented deviation that it would be synchronous "since no background-worker process exists yet."** That worker now exists; this milestone closes that specific, previously-flagged gap rather than opening a new one.
- **Job execution is sequential per worker, not parallelized within a batch** — see Architectural Decisions. Scaling is horizontal (more worker processes), not concurrent execution inside one.

### Known limitations

- `npm run worker` / `npm run worker:once` could not be run against a live database in this environment (no Postgres instance available, the same standing limitation as every other Prisma-backed piece of this project) — verified instead by running the script directly and confirming it resolves all module imports, registers the notification handler, constructs the worker, and reaches (and only fails at) the actual database call, plus the full fake-backed unit/integration suite covering every code path the real repository also implements.
- No admin UI exists for inspecting job history, retry queues, or manually cancelling/re-running a job — `JobRepository.cancel()`/`findById()` exist as ports and are unit-tested, but nothing calls them yet. Out of scope for this milestone (infrastructure + notifications integration only); wiring a "Jobs" admin view is a small additive follow-up.
- Handlers for CSV/Excel export, PDF generation, analytics aggregation, and data cleanup are not implemented — only the infrastructure and one reference integration (notifications) were requested. Adding one is: define a job-type string, implement `JobHandler`, call `jobRegistry.register(...)` from that module's own composition root, and add one import line to `scripts/run-worker.ts`.

## 2026-08-05 — Notification Architecture (Future Extensibility)

Architectural requirement, not a numbered roadmap day: design a generic notification pipeline so that Version 1.0's email-only implementation can grow into WhatsApp/SMS/Push/In-App channels later without ever touching a business use case.

### Added

- **New `notifications` module** (`src/modules/notifications`), matching the module `05_System_Architecture.md` already reserved for this ("Email (and later WhatsApp) dispatch, templated messages — Phase 1"). Full domain/application/infrastructure structure; no `presentation/` layer, since nothing calls this module over HTTP in Version 1.0 — it is only ever invoked internally, by other modules' use cases.
- **`NotificationService` abstraction** (`application/notification-service.ts`): a single `notify({ recipientUserId, template, context })` method. This is the "Business Event → NotificationService → Email Provider" abstraction named in the requirement — callers name a recipient, a template id, and template data; they never see a channel, an email address, or rendered content. Mirrors `AuditRecorder` in `src/lib/audit.ts` (interface for DI; a concrete class implements it), the same pattern already established for a cross-cutting, multi-module concern.
- **`DefaultNotificationService`** (`application/default-notification-service.ts`): the orchestrator wired behind the abstraction. Resolves the recipient's email, persists a `Notification` row (`PENDING`), renders the template, calls the active `EmailProvider`, then marks the row `SENT`/`FAILED`. Depends only on three ports (`EmailProvider`, `NotificationRepository`, `NotificationRecipientLookup`) plus a pure render function — never on Prisma or a concrete provider directly.
- **Two Version 1.0 templates**: `PROFILE_APPROVED` and `PROFILE_CHANGES_REQUESTED`, wired into `ApproveDraftUseCase` and `RequestChangesUseCase` respectively — this closes a real gap (FR-PROF-05 / FR-NOTIFY-01 called for these emails since Days 5–6, but nothing ever sent them; only an audit log entry existed). Each use case now calls `notificationService.notify(...)` once, immediately after its existing `auditRecorder.record(...)` call, with a minimal context (`studentName` for approval; `studentName` + `reviewComment` for changes-requested).
- **Email Template Architecture** (`application/templates/`): every template definition (`definitions/profile-approved.ts`, `definitions/profile-changes-requested.ts`) supplies only `subject()`/`bodyText()`/`bodyHtml()` — pure content. `layout.ts` owns branding and the footer and is applied uniformly by `render.ts`'s `renderEmailTemplate()`; no template file duplicates that markup. A future Rich Email Builder can keep reusing the same `bodyHtml()`/`bodyText()` functions while swapping only the layout wrapper. Reviewer-authored free text (`reviewComment`) is HTML-escaped before interpolation (`escapeHtml()` in `layout.ts`) to prevent HTML injection into a rendered email.
- **`ConsoleEmailProvider`** (`infrastructure/console-email-provider.ts`): the Version 1.0 `EmailProvider` implementation, matching `.env.example`'s `EMAIL_PROVIDER="console"` default — logs the rendered message instead of sending it, so local dev/CI need no real email infrastructure.
- **`createEmailProvider()` factory** (`infrastructure/email-provider-factory.ts`): the swap point named in the requirement ("Development Logger → SMTP → SendGrid → Resend → AWS SES … changing only the infrastructure implementation and environment configuration"). Selects the provider purely from `EMAIL_PROVIDER` (validated env config); adding a real provider later is a new class here plus a new `case`, with zero application-code changes.
- **`src/config/env.ts`** gained `EMAIL_PROVIDER` (enum: `console`/`resend`/`smtp`, default `console`), `EMAIL_FROM_ADDRESS`, and optional `RESEND_API_KEY`/`SMTP_HOST`/`SMTP_PORT`/`SMTP_USER`/`SMTP_PASSWORD` — matching fields `.env.example` already documented since Day 1.
- **`StudentLookup` (profiles module) now also returns `fullName`**, needed to address the notification templates. Purely additive: the field is optional on the in-memory test fake's `seed()` input (defaults to `"Test Student"`) so none of the ~10 existing call sites across profiles' test suite needed changes.
- **Tests** (467 passing, up from 448): `DefaultNotificationService` unit tests covering a successful send, a recipient with no email on file (no-op, nothing persisted), a provider failure (`Notification` row marked `FAILED`, `notify()` still resolves), and a recipient-lookup failure (also swallowed) — directly exercising NFR-AVAIL-03. Template rendering tests (subject/text/html content, HTML-escaping of `reviewComment`, and a shared-layout check proving both templates render the same branding/footer). `ConsoleEmailProvider` and `createEmailProvider()` unit tests. A dedicated privacy regression suite asserting the persisted `Notification.payload` is exactly the caller-supplied context (nothing silently added) and that `ApproveDraftUseCase`/`RequestChangesUseCase`'s real notification context never contains a private-profile-shaped field. `ApproveDraftUseCase`/`RequestChangesUseCase`/state-machine tests updated for the new required `notificationService` dependency (a `FakeNotificationService` fake), plus one new assertion each confirming the exact template and context sent.

### Architectural decisions

- **`NotificationService` lives behind a single, minimal interface (`notify()`), never a channel-aware signature.** Business use cases pass a template id and a data bag; which channel actually gets used is entirely an infrastructure-layer decision. Today that decision is hardcoded to `EMAIL` (the only value `NotificationChannel`/`EmailProvider` support); adding WhatsApp/SMS/Push later means `DefaultNotificationService` gains an internal channel-selection step — `notify()`'s signature, and therefore every existing caller, does not change.
- **Template rendering is a pure function, not a port.** Unlike `EmailProvider`/`NotificationRepository`/`NotificationRecipientLookup` (each genuinely swappable infrastructure), rendering a template involves no I/O — there is nothing to substitute at that boundary, only content to compose. It lives in `application/templates/render.ts` as a plain synchronous function, directly unit-tested without a fake.
- **Notification sending is synchronous (awaited inline), not queued through the existing `Job` table**, even though `06_Technology_Stack.md` describes a database-backed job queue for email specifically. No background worker/poller process exists anywhere in this codebase yet, and building one now — with no existing runtime host to run it in this Next.js deployment — is meaningfully more scope than "wire up two email notifications." The extensibility point is preserved regardless: `NotificationService.notify()`'s signature is identical whether its implementation sends inline or enqueues a job, so switching to queued dispatch later requires changing only `DefaultNotificationService`'s internals, never a calling use case. Flagged here as a deliberate simplification, not a silent gap.
- **`NotificationService` is composed as a ready, bound singleton exported from `notifications/index.ts`** (`export { notificationService } from "./infrastructure/container"`), the same pattern `auth` already established for `withAuth`. `profiles/infrastructure/container.ts` imports it directly, exactly like every other cross-module dependency in this codebase.
- **The module's `container.ts` builds the `EmailProvider` lazily** (cached on first call, not at import time) — the same fix applied to `auth/infrastructure/container.ts` in Days 2–3 for JWT secrets, applied here proactively for `EMAIL_PROVIDER`/env-derived config, so importing `@/modules/notifications` never forces email configuration to exist before the first real notification is sent.

### Security decisions

- **NFR-AVAIL-03 ("a degraded external dependency fails gracefully"):** `DefaultNotificationService.notify()` is designed to never reject. A failure at any stage — recipient lookup, `NotificationRepository` persistence, template rendering, or the `EmailProvider` itself — is caught, logged to `console.error`, and swallowed. `ApproveDraftUseCase`/`RequestChangesUseCase` call `notify()` without a try/catch of their own and are guaranteed a profile approval/changes-requested action can never fail because an email failed to send. Verified directly: a test forces the fake provider to throw and asserts both that `notify()` still resolves and that the `Notification` row is marked `FAILED`.
- **Reviewer-authored free text is HTML-escaped before it reaches a rendered email.** `reviewComment` is student-review free text written by a Coordinator/Secretary, but is nonetheless escaped in `bodyHtml()` before interpolation — a regression test feeds a `<script>` payload as the comment and asserts it never appears unescaped in the rendered HTML.
- **The persisted `Notification.payload` is asserted to be exactly the context the calling use case supplied — nothing added, nothing enriched from elsewhere.** `DefaultNotificationService` has no access to `StudentPrivateProfile` or any admin-only table (unlike the exports/recruiters DTOs, there is no ORM row here to "poison" — the module simply never reads one), and a dedicated regression test confirms `ApproveDraftUseCase`/`RequestChangesUseCase`'s real notification context contains only `studentName`/`reviewComment`, never a private-profile-shaped field (`cgpa`, `phone`, `personalEmail`, `internalRemarks`, etc.).

### Deviations from documentation, flagged rather than assumed

- **Email delivery is synchronous, not queued via the `Job` table**, despite `06_Technology_Stack.md`'s "Background Jobs: Database-Backed Queue (MVP) … polled by a scheduled task handles email sending." See Architectural Decisions above — no job-processing worker exists anywhere in this codebase, and adding one was judged out of scope for wiring up two transactional emails. The `Job` table itself is untouched and available whenever that worker is built.
- **Only the `console` `EMAIL_PROVIDER` is implemented.** `resend` and `smtp` are accepted by env validation (matching `.env.example`) but `createEmailProvider()` throws a clear "not implemented" error for both, since the production email provider is still an open decision (`docs/planning/18_Open_Questions.md`, Q2). Implementing one, once chosen, is additive infrastructure work only.
- **Notification history is limited to the existing `Notification` table's `status`/`sentAt` fields — no new read API or UI was built for it.** The requirement explicitly asked only for this ("Version 1.0 only requires audit logging… do not implement [Sent Notifications/Delivery Status/Read Status/Retry Queue] now, only avoid architectural decisions that would prevent them later"). The schema already supports all four future views without modification; only new read methods on `NotificationRepository` and a UI would be needed to surface them.

### Known limitations

- No notification is sent on draft submission (student → coordinator) — the requirement named only profile approval/changes-requested (FR-PROF-05) and drive announcements (FR-NOTIFY-02, blocked on the Phase 2 `PlacementDrive` entity, which does not exist yet). ### Architectural decisions

- **Each export has its own self-contained Prisma repository rather than reusing students'/batches'/recruiters' use cases directly.** Investigated first: every existing module's public `index.ts` exports only route handlers and types/errors, never raw use-case instances (confirmed by inspecting `students/index.ts` and `batches/index.ts` before writing any export code) — there is no way to call, say, `SearchStudentsUseCase` from another module without either reaching into that module's internals (forbidden by the module-boundary rule) or newly exporting use-case instances from it (a larger, more invasive change to an approved module's public surface than this phase warranted). Given that constraint, building focused, single-purpose queries in the exports module itself — mirroring exactly how the recruiters module was built in Days 8–9 — was the design that respects both "reuse existing use cases wherever appropriate" (there was nothing reusable to call) and "do not modify previous implementation." Flagged as an interpretation, not assumed silently — the alternative reading (Coordinator sees the full unscoped list, same as Secretary) was considered and rejected as inconsistent with "batch-scoped ONLY."

### Security decisions

- **Every mapper is regression-tested against a deliberately "poisoned" input row** — a Prisma-payload-shaped object carrying a password hash, phone number, personal email, CGPA, internal remarks, and a confidential-document reference, as if a future change accidentally widened a query's `include`. None of the four mappers spread their input (`...row`); each reads only its named whitelist of fields, so the poisoned extras never reach the DTO. This is the same technique used for the recruiters module's DTO in Days 8–9, now applied to all four export shapes.
- **Header names themselves are asserted to never contain a forbidden term** (password, hash, cgpa, backlog, personal email, phone, remark, confidential, draft, approval) — catches the case where a future column is added with export-worthy *data* but an accidentally revealing *label*, which a pure data-content test wouldn't catch.
- **The Student Directory query's `include` does pull the full `User` row (including `passwordHash`)** — Prisma has no field-level projection that excludes just one column while including a relation's other fields via a typed include, so the raw database row temporarily holds the hash in memory. The mapper never reads `user.passwordHash`, only `user.email`; the DTO whitelist regression test asserts this holds even when the test deliberately hands the mapper a row where that hash is populated.

Adding it now would mean building Phase 2 schema ahead of its scheduled phase, which the roadmap and every prior day's decisions have deliberately avoided. ## 2026-08-05 — Phase 1, Days 5–6: Two-Profile Workflow (Draft → Review → Publish)

### ⚠️ Documented schema divergence — read before touching this area

`docs/database/08_Database_Design.md` still documents `StudentPublicProfileDraft.status` as the enum `DRAFT | PENDING_REVIEW | APPROVED | REJECTED`. The implemented Prisma schema (`prisma/schema.prisma`) now uses `DRAFT | PENDING_REVIEW | APPROVED | CHANGES_REQUESTED` — `REJECTED` was renamed. This was a genuine conflict between this phase's explicit 5-state request (Draft/Submitted/Pending Review/Changes Requested/Approved) and the frozen 4-value enum; **flagged and resolved with the Secretary before writing any code** (not assumed). The resolution: "Submitted" is a transient action, not a stored state, and `REJECTED` was renamed to `CHANGES_REQUESTED` to reflect that it's a non-terminal state a draft cycles back out of. Per this project's standing instruction to touch only the CHANGELOG when documentation is otherwise frozen, `08_Database_Design.md` itself has deliberately NOT been edited to match — this entry is the authoritative record of the divergence until/unless the Secretary asks for the doc to be updated too.

### Added

- **Profiles module** (`src/modules/profiles`): the draft/approval workflow governing `StudentPublicProfileDraft` and `StudentPublicProfile`, as its own module (matching the module map in `architecture/05_System_Architecture.md`) rather than folded into `students`.
- **A strict 4-state machine**, not boolean flags — `ProfileDraftStatus = "DRAFT" | "PENDING_REVIEW" | "APPROVED" | "CHANGES_REQUESTED"` — with every transition centralized in its own use case and every other transition rejected with a typed `InvalidDraftTransitionError`:
  - **Save draft** (student, own only): DRAFT stays DRAFT; CHANGES_REQUESTED stays CHANGES_REQUESTED (iterative fixes before resubmitting, comment preserved); APPROVED resets to DRAFT (an edit after publication starts a new, unreviewed cycle); PENDING_REVIEW is locked (`DraftLockedForReviewError`) — a reviewer must act first.
  - **Submit** (student, own only; transient action, not a stored state): DRAFT or CHANGES_REQUESTED → PENDING_REVIEW. Any other starting status is rejected.
  - **Approve** (Secretary / in-scope Coordinator only): PENDING_REVIEW → APPROVED, and publishes — the only code path anywhere that writes `StudentPublicProfile`.
  - **Request changes** (Secretary / in-scope Coordinator only, requires a non-empty comment): PENDING_REVIEW → CHANGES_REQUESTED, returning the draft to the student with the reviewer's comment preserved on the draft itself.
- **Publication copies exactly `ProfileContent`** (bio, skills, software, selectedProjects, portfolioLinks, resumeFileId, certifications, internships) from the approved draft into `StudentPublicProfile` — nothing else. There is no shared type spanning `ProfileContent` and `StudentPrivateFields` anywhere in this module's domain layer, so a private field cannot be added to the published payload without visibly redefining the content type; a dedicated test asserts the published object's keys never include `cgpa`, `hasActiveBacklog`, `internalRemarks`, `phone`, or `personalEmail`.
- **`StudentPublicProfile` remains immutable except through approval**: there is no create/update endpoint for it anywhere in the codebase — the only write path is `ApproveDraftUseCase`'s publish step, implemented as an upsert keyed on `studentProfileId` (so re-approval after a later edit updates the same row, never creates a second one).

### Decisions

- **Student account provisioning** (confirmed with the Secretary before implementation): creating a student record automatically creates the linked `User` login row with a securely random, immediately bcrypt-hashed password that is never returned or logged. The student cannot actually log in yet — no password-reset/invite flow exists (FR-AUTH-06 remains open, `planning/18_Open_Questions.md`) — this is a known, deliberate limitation, not an oversight, and unblocks Student CRUD without inventing an undocumented credential-delivery mechanism.
- **Search results include CGPA.** This is intentional: the search/list endpoint is the Secretary/Coordinator-only internal directory, not a public or recruiter-facing surface — CGPA is private data, and this endpoint is exactly the kind of access the permissions matrix already authorizes for those two roles. It must never be reused for the Days 8–9 recruiter directory.
- **Batch-scope validation for the `POST /api/students` (create) endpoint is enforced inside the use case, not via the `withAuth` middleware's `getRequiredBatchId` option.** The target batch ID lives in the request body, and a `Request`'s body stream can only be read once — the middleware and the handler can't both parse it. `CreateStudentUseCase` re-applies the same centralized `canEditPrivateAdminFields` function used everywhere else, so the check isn't skipped, just relocated from middleware to the first line of the use case. All single-resource routes (`GET`/`PATCH`/archive/restore on `/api/students/:id`) still use the middleware-level check, since the batch ID there is resolvable from the route param via an async lookup before the body is ever touched.
- **Fixed a query-building bug found during implementation, before it shipped**: the student search repository's `where` clause was originally assembled as a single object with an `OR` key set twice (once for a skills filter, once for a software filter) — the second silently overwrote the first, since a JS object can only hold one value per key. Restructured as an `AND` array of independent conditions so skills and software filters compose correctly together.
- A small (~15-line) `PasswordHasher`-shaped bcrypt implementation is duplicated in `students/infrastructure/prisma-user-provisioner.ts` rather than reusing the auth module's `BcryptPasswordHasher`, specifically to avoid reaching into another module's infrastructure layer or refactoring already-approved Days 2–3 code for a one-off need (the student provisioner only ever needs to hash a random password once, never `compare()` it). Flagged here since it's a minor, deliberate exception to DRY, not an oversight.

## 2026-08-05 — Phase 1, Days 2–3: Authentication & Authorization Foundation

### Added

- **Application layer (`src/modules/auth/application`)**: ports for `UserRepository`, `RefreshTokenRepository`, `PasswordHasher`, `TokenService`, `AuditRecorder`, and `Clock`; three use cases — `LoginUseCase`, `LogoutUseCase`, `RefreshAccessTokenUseCase` — implementing credential verification, refresh-token rotation with reuse detection, and session termination, entirely independent of Prisma/JWT/bcrypt specifics (Clean Architecture dependency inversion, per `architecture/05_System_Architecture.md`).
- **Domain errors** (`src/modules/auth/domain/errors.ts`): `InvalidCredentialsError`, `InvalidRefreshTokenError`, `RefreshTokenExpiredError`, `RefreshTokenReusedError` — typed, no generic thrown strings.
- **Infrastructure**: `BcryptPasswordHasher` (cost factor 12+ enforced at construction, refuses to build otherwise), `JwtTokenService` (short-lived signed access tokens; opaque, high-entropy refresh tokens hashed via keyed HMAC-SHA256 rather than bcrypt — see "Security decisions" below), Prisma-backed `UserRepository`/`RefreshTokenRepository`/`AuditRecorder`, an in-memory fixed-window `InMemoryRateLimiter` for login throttling (FR-AUTH-05), and a lazily-initializing composition root (`container.ts`).
- **Session management**: refresh tokens delivered exclusively via an httpOnly, `Secure` (in production), `SameSite=Strict` cookie scoped to `/api/auth`; access tokens returned in the JSON response body for `Authorization: Bearer` use. Logout and rotation-reuse detection both revoke the full token family, not just one token.
- **`withAuth` middleware** (`src/modules/auth/presentation/with-auth.ts`): implements the required Request → Authentication → JWT Validation → Role Validation → Batch Scope Validation → Business Logic flow as a single reusable wrapper, backed entirely by the existing permissions primitives from Day 1 — no route handler re-implements a role or scope check.
- **Route handlers**: `POST /api/auth/login`, `POST /api/auth/logout`, `POST /api/auth/refresh`, and a protected `GET /api/auth/me` demonstrating the full middleware chain end to end (no Student/Batch/Profile module exists yet — that's Days 3–6 — so `/me` exists purely to prove the auth foundation itself).
- **Audit hooks**: `LOGIN_SUCCESS`, `LOGIN_FAILED` (when the account exists), `LOGOUT`, and `REFRESH_TOKEN_REUSE_DETECTED` are recorded to the existing `AuditLog` table via the `AuditRecorder` port, per this phase's "prepare for later, no UI yet" scope.
- **Tests** (79 passing, up from 24): unit tests for `BcryptPasswordHasher`, `JwtTokenService`, and all three use cases (via in-memory fakes for every port — no real database required to test business logic); an integration-style suite for the `withAuth` middleware chain covering unauthenticated/invalid/expired/tampered tokens, role restrictions, and batch-scope restrictions, explicitly including the brief's two named boundaries (Coordinator cross-batch denial, Recruiter total denial) at the middleware level in addition to Day 1's coverage at the permission-function level.

### Security decisions

- **Refresh tokens are hashed with keyed HMAC-SHA256, not bcrypt.** The brief's bcrypt requirement targets user-chosen passwords, which are low-entropy and need slow, salted hashing to resist brute force. Refresh tokens are the opposite: 256-bit random values generated by the server, already unguessable, and needed for fast, deterministic lookup-by-hash on every refresh request — which a randomly-salted bcrypt hash cannot support (there is no way to look up a row by hash without either storing the salt separately or comparing against every stored hash). A keyed HMAC is the standard, correct tool for this case and is still never stored in plaintext, still revocable (`revokedAt`), and still rotated on every use.
- **Access tokens travel as a Bearer token in the JSON response body, not a cookie.** Only the refresh token needed the httpOnly-cookie treatment (documentation requirement). Keeping the access token out of cookies avoids CSRF exposure on every authenticated request; it lives in memory on the client and is attached explicitly via `Authorization: Bearer`.
- **Role/batch scope are embedded directly in the access token's claims** (`role`, `batchScope`, `studentProfileId`), resolved once at login/refresh time rather than re-queried from the database on every request. This avoids a database round-trip per request; the staleness window is bounded by the access token's short lifetime (minutes) and self-corrects on the next refresh.
- **Login always performs a real bcrypt comparison, even for a non-existent email**, against a precomputed dummy hash of matching cost, so response timing does not reveal whether an account exists.
- **The composition root lazily constructs anything that depends on validated environment configuration** (bcrypt cost factor, JWT secrets, token TTLs), rather than at module import time. This was a mid-implementation fix: the Day 1 permissions test (which imports only pure domain functions via the module's public `index.ts`) started failing once `index.ts` also re-exported the `withAuth`/route-handler surface, because JS module evaluation eagerly runs a barrel file's entire import graph regardless of which named export is actually used — so importing one pure function was transitively forcing environment/secret validation to run. Fixed by making `src/config/env.ts` and the composition root resolve lazily, on first real use, and caching after. This is an implementation detail, not an architecture or documentation change.
